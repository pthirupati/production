# 0003 — RS256 JWTs signed with a dedicated keypair

**Status:** Accepted
**Written:** 2026-08 (retrospectively)

## Context

Django's default is HS256 signed with `SECRET_KEY`. That couples two things that
have different lifecycles: the framework secret (used for CSRF, sessions, signed
cookies) and the token-signing key.

The practical consequence showed up in operations. `SECRET_KEY` is the thing you
rotate on suspicion; token signing is the thing you must *not* rotate casually,
because it logs everyone out.

## Decision

`SIMPLE_JWT["ALGORITHM"] = "RS256"` with a separate RSA keypair
(`JWT_RSA_PRIVATE_KEY` / PEM on disk), independent of `SECRET_KEY`.

## Consequences

- `SECRET_KEY` can be rotated without invalidating a single session. The only
  casualty is unsubscribe links already in flight, which are signed with it.
- Conversely, rotating the JWT keypair *is* a deliberate mass logout — which is
  the correct semantics for that action, and is why the deploy flag that rotates
  secrets has historically broken login when flipped by accident.
- Only the private key can mint tokens; the public key verifies. If verification
  ever needs to move to another service, that is now possible without shipping a
  signing secret.
- More moving parts: a keypair to generate, store and mount. A missing key means
  the process will not boot — noisy, which is the right failure mode.

## Alternatives rejected

- **HS256 on `SECRET_KEY`.** Simplest, and it makes "rotate the framework secret"
  and "log everyone out" the same operation.
- **HS256 on a separate secret.** Gets the lifecycle separation without asymmetric
  keys, but keeps signing and verification as the same capability.
